# LangGraph для пачаткоўцаў: Поўны дапаможнік

> **Што вы даведаецеся:** Як будаваць AI-агентныя сістэмы з LangGraph — ад базавых канцэпцый да працуючага кода. Мы створым пайплайн для напісання артыкулаў з некалькімі AI-агентамі, якія супрацоўнічаюць, правяраюць працу адзін аднаго і ітэруюць, пакуль вынік не будзе ідэальным.

---

## ЧАСТКА 1: Базавыя канцэпцыі

### Што такое граф?

Перш чым разбірацца з LangGraph, трэба зразумець, што такое **граф** у праграмаванні.

#### Граф — гэта структура даных

Уявіце карту метро:

- **Станцыі** — гэта **вузлы** (nodes)
- **Лініі паміж станцыямі** — гэта **пераходы** (edges)

```
    Звычайны граф:              Карта метро (аналогія):

        [A]                         [Плошча Перамогі]
         │                                 │
         ▼                                 ▼
        [B]───────►[C]              [Кастрычніцкая]───►[Купалаўская]
         │                                 │
         ▼                                 ▼
        [D]                         [Інстытут культуры]
```

#### У LangGraph:

- **Вузлы** — гэта функцыі (агенты), якія нешта робяць.
- **Пераходы** — гэта правілы, хто пасля каго працуе.

---

### Навошта патрэбны LangGraph?

#### Праблема: Звычайныя AI-праграмы лінейныя

```
Звычайны ланцужок (Chain):

    Пытанне → LLM → Адказ

    або

    Пытанне → Інструмент 1 → LLM → Інструмент 2 → Адказ
```

Гэта працуе для простых задач, але што, калі:

- Трэба **вярнуцца назад** і перарабіць?
- Трэба **праверыць вынік** і, магчыма, паўтарыць?
- Трэба **некалькі агентаў** з рознымі ролямі?

#### Рашэнне: LangGraph дазваляе ствараць цыклы

```
LangGraph (Граф):

                    ┌──────────────────────┐
                    │                      │
                    ▼                      │
    Пытанне → [Даследчык] → [Пісьменнік] → [Рэцэнзент]
                                               │
                                               ▼
                                          Добра? ───НЕ───► назад да Пісьменніка
                                               │
                                              ТАК
                                               │
                                               ▼
                                           [Вынік]
```

---

### Што такое "стан" (State)?

#### Стан — гэта памяць праграмы

Уявіце, што вы пішаце артыкул з камандай:

- Даследчык сабраў **матэрыялы** → трэба некуды запісаць.
- Пісьменнік напісаў **чарнавік** → трэба перадаць рэцэнзенту.
- Рэцэнзент напісаў **заўвагі** → трэба вярнуць пісьменніку.

**Стан** — гэта "кошык", куды ўсе кладуць свае вынікі і адкуль бяруць даныя.

```
┌─────────────────────────────────────────────────────────────┐
│                         СТАН (State)                        │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   topic: "Пра што пішам"                                    │
│   research: "Матэрыялы ад даследчыка"                       │
│   draft: "Чарнавік ад пісьменніка"                          │
│   review: "Заўвагі ад рэцэнзента"                           │
│   finalArticle: "Гатовы артыкул"                            │
│   messages: [гісторыя ўсіх паведамленняў]                   │
│                                                             │
└─────────────────────────────────────────────────────────────┘
         ▲                    ▲                    ▲
         │                    │                    │
    Даследчык            Пісьменнік           Рэцэнзент
    (чытае і піша)       (чытае і піша)       (чытае і піша)
```

## ЧАСТКА 2: Annotation — Як ствараецца стан

### Што такое Annotation?

`Annotation` — гэта спосаб **апісання структуры стану**. Гэта як стварэнне формы з палямі.

#### Аналогія: Анкета

Уявіце, што вы ствараеце анкету:

```
┌─────────────────────────────────────────┐
│            АНКЕТА РАБОТНІКА             │
├─────────────────────────────────────────┤
│ Імя: ___________________                │
│ Узрост: _____                           │
│ Вопыт працы (гады): _____               │
│ Спіс навыкаў: ___, ___, ___             │
└─────────────────────────────────────────┘
```

У кодзе гэта выглядае так:

```typescript
// АНАЛОГІЯ: Стварэнне формы анкеты
const Anketa = {
    imya: '', // Тэкставае поле
    uzrost: 0, // Лік
    vopyt: 0, // Лік
    navyki: [], // Спіс
};
```

#### У LangGraph: Annotation.Root

У LangGraph стан ствараецца з дапамогай `Annotation.Root()`. Гэта спецыяльная функцыя, якая апісвае структуру вашых даных — якія палі існуюць і як яны павінны абнаўляцца.

```typescript
import { Annotation } from '@langchain/langgraph';

const ResearchState = Annotation.Root({
    // Кожнае поле апісваецца праз Annotation<Тып>
    topic: Annotation<string>({...}),
    research: Annotation<string>({...}),
    draft: Annotation<string>({...}),
    // і г.д.
});
```

Кожнае поле ўнутры `Annotation.Root` мае дзве важныя ўласцівасці: **reducer** (як абнаўляць значэнне) і **default** (пачатковае значэнне). Мы разбяром іх далей.

---

### Што такое Reducer?

#### Праблема: Як аб'ядноўваць даныя?

Калі некалькі агентаў пішуць у адно поле, што рабіць?

```
Агент 1 піша: topic = "Тэма А"
Агент 2 піша: topic = "Тэма Б"

Што павінна быць у topic? "Тэма А"? "Тэма Б"? "Тэма А + Тэма Б"?
```

#### Рашэнне: Reducer — функцыя, якая вырашае

**Reducer** — гэта функцыя, якая атрымлівае:

1. **Бягучае значэнне** (што ўжо ёсць)
2. **Новае значэнне** (што прыйшло)

І вяртае: **вынік** (што захаваць)

```typescript
reducer: (current, update) => результат;
//         ▲         ▲           ▲
//         │         │           └── Што захаваецца
//         │         └── Новае значэнне
//         └── Бягучае значэнне
```

#### Прыклады Reducer-аў:

##### 1. Reducer "ЗАМЯНІЦЬ" (replace)

Новае значэнне поўнасцю замяняе старое.

```typescript
// Код:
reducer: (current, update) => update;

// Прыклад:
// Бягучае: "Тэма А"
// Новае:   "Тэма Б"
// Вынік:   "Тэма Б"  ← новае замяніла старое
```

**Аналогія:** Вы перазапісваеце файл — новы змест замяняе стары.

```
файл.txt
──────────────
Было:   "Стары тэкст"
        ▼ (перазапіс)
Стала:  "Новы тэкст"
```

##### 2. Reducer "ДАДАЦЬ" (append)

Новыя элементы дадаюцца да існуючых.

```typescript
// Код:
reducer: (current, update) => [...current, ...update];

// Прыклад:
// Бягучае: ["Паведамленне 1", "Паведамленне 2"]
// Новае:   ["Паведамленне 3"]
// Вынік:   ["Паведамленне 1", "Паведамленне 2", "Паведамленне 3"]
```

**Аналогія:** Вы дадаеце новыя запісы ў дзённік — старыя застаюцца.

```
дзённік.txt
──────────────
Было:   "Панядзелак: зрабіў А"
        "Аўторак: зрабіў Б"
        ▼ (дадаём)
Стала:  "Панядзелак: зрабіў А"
        "Аўторак: зрабіў Б"
        "Серада: зрабіў В"  ← дадалося
```

#### Поўны прыклад стану:

```typescript
const ResearchState = Annotation.Root({
    // ═══════════════════════════════════════════════════════
    // ПОЛЕ: messages (паведамленні)
    // ═══════════════════════════════════════════════════════
    messages: Annotation<BaseMessage[]>({
        // REDUCER: Дадаваць новыя паведамленні да існуючых
        reducer: (current, update) => [...current, ...update],
        // DEFAULT: Пачатковае значэнне — пусты масіў
        default: () => [],
    }),
    //
    // Як гэта працуе:
    // 1. Пачатак:    messages = []
    // 2. Даследчык:  messages = [] + [AIMessage] = [AIMessage]
    // 3. Пісьменнік: messages = [AIMessage] + [AIMessage] = [AIMessage, AIMessage]
    // 4. І г.д. — усе паведамленні захоўваюцца

    // ═══════════════════════════════════════════════════════
    // ПОЛЕ: topic (тэма)
    // ═══════════════════════════════════════════════════════
    topic: Annotation<string>({
        // REDUCER: Замяняць старое значэнне новым
        reducer: (_, update) => update, // "_" значыць "ігнаруем"
        // DEFAULT: Пачатковае значэнне — пусты радок
        default: () => '',
    }),
    //
    // Як гэта працуе:
    // 1. Пачатак:    topic = ""
    // 2. Карыстач:   topic = "" → "LangChain"
    // Калі хтось яшчэ напіша ў topic — старое значэнне знікне

    // ═══════════════════════════════════════════════════════
    // ПОЛЕ: iterationCount (лічыльнік ітэрацый)
    // ═══════════════════════════════════════════════════════
    iterationCount: Annotation<number>({
        reducer: (_, update) => update, // Проста замяняем
        default: () => 0, // Пачынаем з 0
    }),
    //
    // Пісьменнік кожны раз піша: iterationCount: state.iterationCount + 1
    // 1. Пачатак:         iterationCount = 0
    // 2. Пісьменнік (1):  iterationCount = 0 + 1 = 1
    // 3. Пісьменнік (2):  iterationCount = 1 + 1 = 2
    // 4. Пісьменнік (3):  iterationCount = 2 + 1 = 3
});
```

#### Візуалізацыя Reducer-аў:

```
┌─────────────────────────────────────────────────────────────────┐
│                    REDUCER: ЗАМЯНІЦЬ                            │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   Бягучае:  █████████████  "Стары тэкст"                        │
│                   ▼                                             │
│   Новае:    ░░░░░░░░░░░░░  "Новы тэкст"                         │
│                   ▼                                             │
│   Вынік:    ░░░░░░░░░░░░░  "Новы тэкст"  ← толькі новае         │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│                    REDUCER: ДАДАЦЬ                              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│   Бягучае:  [█] [█] [█]         ← тры элементы                  │
│                   +                                             │
│   Новае:    [░] [░]             ← два новыя                     │
│                   =                                             │
│   Вынік:    [█] [█] [█] [░] [░] ← усе разам                     │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

---

### Што такое default?

`default` — гэта функцыя, якая вяртае **пачатковае значэнне** поля.

```typescript
default: () => значэнне
```

#### Чаму функцыя, а не проста значэнне?

Гэта распаўсюджаная пастка JavaScript. Калі вы выкарыстоўваеце просты аб'ект або масіў як default, усе экзэмпляры будуць спасылацца на адну і тую ж спасылку — змены ў адным месцы паўплываюць на ўсе астатнія!

```typescript
// ДРЭННА: Калі гэта аб'ект або масіў
default: []  // Усе экзэмпляры будуць спасылацца на адзін масіў!

// ДОБРА: Функцыя стварае новы масіў кожны раз
default: () => []  // Кожны экзэмпляр атрымае свой масіў
```

#### Прыклады:

```typescript
// Для радка
default: () => ''        // Пусты радок

// Для ліку
default: () => 0         // Нуль

// Для масіва
default: () => []        // Пусты масіў

// Для аб'екта
default: () => ({})      // Пусты аб'ект

// Для boolean
default: () => false     // false
```

## ЧАСТКА 3: Вузлы (Nodes) — Агенты

### Што такое вузел?

**Вузел (Node)** — гэта функцыя, якая:

1. **Атрымлівае** поўны стан
2. **Робіць** нейкую працу (напрыклад, выклікае LLM)
3. **Вяртае** частковае абнаўленне стану

#### Аналогія: Работнік на канвееры

```
┌─────────────────────────────────────────────────────────────┐
│                         КАНВЕЕР                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   [Каробка] ──► [Работнік 1] ───────► [Работнік 2] ──────►  │
│                    │                      │                 │
│                    ▼                      ▼                 │
│              Дадае дэталь А         Дадае дэталь Б          │
│                                                             │
└─────────────────────────────────────────────────────────────┘

Кожны работнік:
1. Бачыць, што ўжо зроблена (стан)
2. Робіць сваю частку работы
3. Перадае далей з дапаўненнямі
```

#### Структура вузла ў кодзе:

```typescript
async function myNode(
    state: ResearchStateType // ← УВАХОД: Поўны стан
): Promise<Partial<ResearchStateType>> {
    // ← ВЫХАД: Частковае абнаўленне
    // 1. Чытаем даныя са стану
    const data = state.someField;

    // 2. Робім працу
    const result = await doSomething(data);

    // 3. Вяртаем абнаўленне (толькі тое, што змянілі)
    return {
        someField: result,
    };
}
```

#### Важна: Partial<State>

Вузел не абавязаны вяртаць увесь стан — толькі палі, якія змяніліся. LangGraph аб'яднае вашае частковае абнаўленне з існуючым станам з дапамогай reducer-аў, якія вы вызначылі.

```typescript
// Поўны стан мае 6 палёў:
state = {
    topic: "...",
    research: "...",
    draft: "...",
    review: "...",
    finalArticle: "...",
    messages: [...],
    iterationCount: 0
}

// Але вузел можа вярнуць толькі тое, што змяніў:
return {
    draft: "Новы чарнавік",           // Змянілі
    messages: [new AIMessage("...")], // Дадалі
    // Астатнія палі не згадваем — яны застануцца як былі
}
```

### Нашы вузлы падрабязна

Цяпер разгледзім чатыры вузлы ў нашай сістэме напісання артыкулаў. Кожны вузел мае канкрэтную ролю і перадае свае вынікі наступнаму праз агульны стан.

#### Вузел 1: Даследчык (researcherNode)

Даследчык — першы агент у нашым пайплайне. Ён бярэ тэму і генеруе даследчыя матэрыялы, якія будуць выкарыстоўвацца пісьменнікам.

```typescript
async function researcherNode(
    state: ResearchStateType
): Promise<Partial<ResearchStateType>> {
    // ┌─────────────────────────────────────────────────────────────┐
    // │ КРОК 1: Атрымліваем тэму для даследавання                  │
    // └─────────────────────────────────────────────────────────────┘
    const topic =
        state.topic ||
        String(state.messages[state.messages.length - 1]?.content) ||
        '';
    //            ▲               ▲
    //            │               └── Альбо апошняе паведамленне
    //            └── Спачатку спрабуем узяць topic

    // ┌─────────────────────────────────────────────────────────────┐
    // │ КРОК 2: Фармуем prompt для LLM                             │
    // └─────────────────────────────────────────────────────────────┘
    const prompt = `Ты эксперт-даследчык. Твая задача - сабраць ключавую інфармацыю.
    Тэма: ${topic}
    Правядзі кароткае даследаванне...`;

    // ┌─────────────────────────────────────────────────────────────┐
    // │ КРОК 3: Выклікаем LLM                                      │
    // └─────────────────────────────────────────────────────────────┘
    const response = await model.invoke([
        { role: 'system', content: prompt }, // Інструкцыі для AI
        { role: 'user', content: `Даследуй тэму: ${topic}` }, // Запыт
    ]);

    const research = String(response.content); // Вынік ад LLM

    // ┌─────────────────────────────────────────────────────────────┐
    // │ КРОК 4: Вяртаем абнаўленне стану                           │
    // └─────────────────────────────────────────────────────────────┘
    return {
        research, // Запісваем вынік даследавання
        messages: [
            new AIMessage({ content: `[Даследаванне завершана]\n${research}` }),
        ],
        // ▲ Дадаем паведамленне ў гісторыю
    };
}
```

**Што адбываецца:**

```
УВАХОД (state):                    ВЫХАД (абнаўленне):
┌─────────────────────┐            ┌─────────────────────┐
│ topic: "LangChain"  │            │ research: "LangCh.. │
│ research: ""        │  ──────►   │ messages: [+1 msg]  │
│ draft: ""           │            └─────────────────────┘
│ messages: [1 msg]   │
└─────────────────────┘

                                    ▼ Пасля аб'яднання:
                               ┌─────────────────────┐
                               │ topic: "LangChain"  │
                               │ research: "LangCh...│ ← абноўлена
                               │ draft: ""           │
                               │ messages: [2 msgs]  │ ← дадалося
                               └─────────────────────┘
```

#### Вузел 2: Пісьменнік (writerNode)

Пісьменнік бярэ даследаванне і стварае чарнавік артыкула. Калі гэта перапрацоўка (пасля водгукаў рэцэнзента), ён таксама ўлічвае каментары да рэцэнзіі. Звярніце ўвагу, як `iterationCount` дапамагае адсочваць, колькі разоў артыкул быў перапісаны.

```typescript
async function writerNode(
    state: ResearchStateType
): Promise<Partial<ResearchStateType>> {
    // ┌─────────────────────────────────────────────────────────────┐
    // │ КРОК 1: Чытаем даследаванне і магчымую рэцэнзію            │
    // └─────────────────────────────────────────────────────────────┘
    const prompt = `Ты тэхнічны пісьменнік. На аснове даследавання напішы артыкул.

Даследаванне:
${state.research}

${
    state.review
        ? `Папярэдняя рэцэнзія (улічы заўвагі):
${state.review}`
        : ''
}
`;

    // ┌─────────────────────────────────────────────────────────────┐
    // │ КРОК 2: Выклікаем LLM                                       │
    // └─────────────────────────────────────────────────────────────┘
    const response = await model.invoke([
        { role: 'system', content: prompt },
        { role: 'user', content: 'Напішы артыкул на аснове даследавання' },
    ]);

    const draft = String(response.content);

    // ┌─────────────────────────────────────────────────────────────┐
    // │ КРОК 3: Вяртаем абнаўленне                                  │
    // └─────────────────────────────────────────────────────────────┘
    return {
        draft, // Чарнавік артыкула
        iterationCount: state.iterationCount + 1, // Павялічваем лічыльнік
        messages: [
            new AIMessage({
                content: `[Чарнавік ${state.iterationCount + 1}]`,
            }),
        ],
    };
}
```

**Што адбываецца пры паўторным выкліку:**

```
ПЕРШЫ ВЫКЛІК:                      ДРУГІ ВЫКЛІК (пасля рэцэнзіі):
┌─────────────────────┐            ┌─────────────────────┐
│ research: "..."     │            │ research: "..."     │
│ review: ""          │            │ review: "Дапрацуй...│ ← ёсць заўвагі!
│ iterationCount: 0   │            │ iterationCount: 1   │
└─────────────────────┘            └─────────────────────┘
         │                                   │
         ▼                                   ▼
  Піша без заўваг                   Улічвае заўвагі
         │                                   │
         ▼                                   ▼
┌─────────────────────┐            ┌─────────────────────┐
│ draft: "Версія 1"   │            │ draft: "Версія 2"   │
│ iterationCount: 1   │            │ iterationCount: 2   │
└─────────────────────┘            └─────────────────────┘
```

#### Вузел 3: Рэцэнзент (reviewerNode)

Рэцэнзент ацэньвае чарнавік і вырашае, ці гатовы ён да публікацыі. Ключавы момант тут — вывад: калі рэцэнзія змяшчае "ЗАЦВЕРДЖАНА", артыкул ідзе на фіналізацыю. У адваротным выпадку ён вяртаецца да пісьменніка для паляпшэнняў. Менавіта гэта дазваляе ствараць **цыкл** у нашым графе.

```typescript
async function reviewerNode(state: ResearchStateType): Promise<Partial<ResearchStateType>> {

    // ┌─────────────────────────────────────────────────────────────┐
    // │ КРОК 1: Фармуем запыт на рэцэнзію                          │
    // └─────────────────────────────────────────────────────────────┘
    const prompt = `Ты строгі рэдактар. Ацані артыкул.

Артыкул:
${state.draft}

Ацані па крытэрыях:
1. Дакладнасць інфармацыі
2. Структура і лагічнасць
3. Якасць мовы
4. Паўната раскрыцця тэмы

Калі артыкул добры - скажы "ЗАЦВЕРДЖАНА".
Калі трэба дапрацаваць - дай канкрэтныя рэкамендацыі.`;

    // ┌─────────────────────────────────────────────────────────────┐
    // │ КРОК 2: Атрымліваем рэцэнзію                                │
    // └─────────────────────────────────────────────────────────────┘
    const response = await model.invoke([...]);
    const review = String(response.content);

    // ┌─────────────────────────────────────────────────────────────┐
    // │ КРОК 3: Вяртаем рэцэнзію                                    │
    // └─────────────────────────────────────────────────────────────┘
    return {
        review,  // Рэцэнзія (або "ЗАЦВЕРДЖАНА" або заўвагі)
        messages: [new AIMessage({ content: `[Рэцэнзія]\n${review}` })],
    };
}
```

**Два магчымыя вынікі:**

```
ВАРЫЯНТ А: Артыкул добры           ВАРЫЯНТ Б: Трэба дапрацаваць
┌─────────────────────────┐        ┌─────────────────────────┐
│ review: "ЗАЦВЕРДЖАНА.   │        │ review: "Дапрацаваць:   │
│ Артыкул выдатны!"       │        │ 1. Дадай прыклады       │
│                         │        │ 2. Удакладні тэрміны"   │
└─────────────────────────┘        └─────────────────────────┘
         │                                   │
         ▼                                   ▼
    Ідзём да                           Вяртаемся да
    finalizer                          writer
```

#### Вузел 4: Фіналізатар (finalizerNode)

Фіналізатар — найпрасцейшы вузел — ён проста капіюе зацверджаны чарнавік у поле `finalArticle`, пазначаючы канец нашага працоўнага працэсу. Ён выклікаецца, калі рэцэнзент зацвярджае артыкул.

```typescript
async function finalizerNode(
    state: ResearchStateType
): Promise<Partial<ResearchStateType>> {
    // Просты вузел — капіюе чарнавік у фінальны артыкул
    return {
        finalArticle: state.draft, // Гатовы артыкул
        messages: [new AIMessage({ content: `[ГАТОВА]\n\n${state.draft}` })],
    };
}
```

**Што адбываецца:**

```
УВАХОД:                            ВЫХАД:
┌─────────────────────┐            ┌─────────────────────┐
│ draft: "Гатовы..."  │ ──────►    │ finalArticle:       │
│ finalArticle: ""    │            │   "Гатовы..."       │
└─────────────────────┘            └─────────────────────┘
```

## ЧАСТКА 4: Пераходы (Edges)

### Што такое пераход?

**Пераход (Edge)** — гэта правіла, якое кажа: "Пасля гэтага вузла выконваецца той вузел".

#### Аналогія: Стрэлкі на схеме

```
Рэцэпт пічы:

    [Зрабіць цеста] ─────► [Дадаць соус] ─────► [Дадаць сыр] ─────► [Выпекчы]
           │                     │                    │                 │
           ▼                     ▼                    ▼                 ▼
       ПЕРАХОД              ПЕРАХОД              ПЕРАХОД           КАНЕЦ
```

#### Два тыпы пераходаў у LangGraph:

##### 1. Простыя пераходы (addEdge)

**Заўсёды** ідзём у адзін і той жа вузел.

```typescript
workflow.addEdge('researcher', 'writer');
//                    ▲            ▲
//                    │            └── Куды ідзём
//                    └── Адкуль ідзём

// Значыць: Пасля researcher ЗАЎСЁДЫ ідзём да writer
```

**Візуалізацыя:**

```
    [researcher] ───────────────► [writer]
                   (заўсёды)
```

##### 2. Умоўныя пераходы (addConditionalEdges)

Выбар наступнага вузла **залежыць ад стану**.

```typescript
workflow.addConditionalEdges(
    'reviewer', // Адкуль ідзём
    shouldContinue, // Функцыя, якая вырашае куды
    {
        writer: 'writer', // Калі функцыя верне 'writer' → ідзём у writer
        finalizer: 'finalizer', // Калі функцыя верне 'finalizer' → ідзём у finalizer
    }
);
```

**Візуалізацыя:**

```
                            ┌──────────► [writer]
                            │
    [reviewer] ─────► [?] ──┤
                            │
                            └──────────► [finalizer]

    Функцыя shouldContinue вырашае, якую стрэлку абраць
```

---

### Функцыя shouldContinue падрабязна

Гэта "мозг" нашага ўмоўнага пераходу. Ён аналізуе бягучы стан і вырашае, куды ісці далей. Функцыя павінна вярнуць радок, які адпавядае аднаму з ключоў у аб'екце супастаўлення, вызначаным у `addConditionalEdges`.

```typescript
function shouldContinue(state: ResearchStateType): 'writer' | 'finalizer' {
    //                                              ▲
    //                                              └── Вяртае адзін з гэтых радкоў

    const review = state.review.toLowerCase();
    const maxIterations = 3;

    // ═══════════════════════════════════════════════════════════════
    // УМОВА 1: Рэцэнзент сказаў "ЗАЦВЕРДЖАНА"
    // ═══════════════════════════════════════════════════════════════
    if (review.includes('зацверджана') || review.includes('approved')) {
        console.log('Артыкул зацверджаны');
        return 'finalizer'; // ← Ідзём завяршаць
    }

    // ═══════════════════════════════════════════════════════════════
    // УМОВА 2: Занадта шмат спробаў (абарона ад бясконцага цыкла)
    // ═══════════════════════════════════════════════════════════════
    if (state.iterationCount >= maxIterations) {
        console.log('Дасягнуты максімум ітэрацый');
        return 'finalizer'; // ← Прымусова завяршаем
    }

    // ═══════════════════════════════════════════════════════════════
    // ІНАКШ: Патрэбна дапрацоўка
    // ═══════════════════════════════════════════════════════════════
    console.log('Патрабуецца дапрацоўка');
    return 'writer'; // ← Вяртаемся да пісьменніка
}
```

#### Блок-схема рашэння:

```
                         ┌───────────────────┐
                         │  shouldContinue   │
                         │    (функцыя)      │
                         └─────────┬─────────┘
                                   │
                                   ▼
                    ┌──────────────────────────────┐
                    │ Ці ёсць "зацверджана"        │
                    │ у рэцэнзіі?                  │
                    └──────────────┬───────────────┘
                                   │
                      ┌────────────┴────────────┐
                      │                         │
                     ТАК                       НЕ
                      │                         │
                      ▼                         ▼
               ┌────────────┐      ┌──────────────────────────┐
               │  return    │      │ Ці iterationCount >= 3?  │
               │'finalizer' │      └──────────────┬───────────┘
               │            │                     │
               └────────────┘        ┌────────────┴────────────┐
                                     │                         │
                                    ТАК                       НЕ
                                     │                         │
                                     ▼                         ▼
                              ┌────────────┐            ┌────────────┐
                              │  return    │            │  return    │
                              │'finalizer' │            │  'writer'  │
                              │            │            │            │
                              └────────────┘            └────────────┘
```

### Як будуецца граф

Цяпер давайце злучым усё разам! Пабудова графа ў LangGraph ідзе па простым шаблоне: стварыць граф, дадаць вузлы, злучыць іх пераходамі і скампіляваць.

#### Паслядоўнасць стварэння:

```typescript
// ═══════════════════════════════════════════════════════════════
// КРОК 1: Ствараем StateGraph з нашым станам
// ═══════════════════════════════════════════════════════════════
const workflow = new StateGraph(ResearchState)

    // ═══════════════════════════════════════════════════════════
    // КРОК 2: Дадаем вузлы (рэгіструем функцыі)
    // ═══════════════════════════════════════════════════════════
    .addNode('researcher', researcherNode) // Імя 'researcher' → функцыя
    .addNode('writer', writerNode) // Імя 'writer' → функцыя
    .addNode('reviewer', reviewerNode) // Імя 'reviewer' → функцыя
    .addNode('finalizer', finalizerNode) // Імя 'finalizer' → функцыя

    // ═══════════════════════════════════════════════════════════
    // КРОК 3: Дадаем простыя пераходы
    // ═══════════════════════════════════════════════════════════
    .addEdge('__start__', 'researcher') // Пачатак → Даследчык
    .addEdge('researcher', 'writer') // Даследчык → Пісьменнік
    .addEdge('writer', 'reviewer') // Пісьменнік → Рэцэнзент

    // ═══════════════════════════════════════════════════════════
    // КРОК 4: Дадаем умоўны пераход
    // ═══════════════════════════════════════════════════════════
    .addConditionalEdges('reviewer', shouldContinue, {
        writer: 'writer', // Калі 'writer' → назад да пісьменніка
        finalizer: 'finalizer', // Калі 'finalizer' → да фіналізатара
    })

    // ═══════════════════════════════════════════════════════════
    // КРОК 5: Дадаем канчатковы пераход
    // ═══════════════════════════════════════════════════════════
    .addEdge('finalizer', '__end__'); // Фіналізатар → Канец
```

#### Спецыяльныя вузлы:

```
┌─────────────────────────────────────────────────────────────┐
│  '__start__'  │  Віртуальны пачатковы вузел                │
│               │  LangGraph аўтаматычна пачынае з яго        │
├───────────────┼─────────────────────────────────────────────┤
│  '__end__'    │  Віртуальны канчатковы вузел               │
│               │  Калі дайшлі да яго — граф завяршыўся       │
└─────────────────────────────────────────────────────────────┘
```

## ЧАСТКА 5: Кампіляцыя і запуск

Мы вызначылі наш стан, вузлы і пераходы. Цяпер час ператварыць гэты чарцёж у працуючае прыкладанне!

### Што такое compile()?

`compile()` — гэта працэс пераўтварэння **апісання графа** ў **выканальную праграму**. Пакуль вы не выклічаце `compile()`, у вас ёсць толькі апісанне таго, што вы хочаце пабудаваць — а не рэальна працуючая сістэма.

```typescript
// Апісанне графа (blueprint)
const workflow = new StateGraph(ResearchState)
    .addNode(...)
    .addEdge(...);

// Кампіляцыя ў выканальную праграму
const app = workflow.compile();
//    ▲
//    └── Цяпер гэта можна запускаць!
```

#### Аналогія: Рэцэпт vs. Гатовая страва

```
workflow (апісанне)              app (скампіляваная праграма)
────────────────────            ──────────────────────────────
Рэцэпт на паперы                 Гатовая піца
   - Як рабіць цеста                (можна есці)
   - Што дадаваць
   - Як выпякаць

Нельга есці!                     Можна есці!
```

---

### Checkpointer (MemorySaver)

#### Што гэта такое?

**Checkpointer** — гэта механізм для **захавання стану** пасля кожнага кроку.

```typescript
import { MemorySaver } from '@langchain/langgraph';

const checkpointer = new MemorySaver();

const app = workflow.compile({
    checkpointer, // ← Дадаем checkpointer
});
```

#### Навошта гэта патрэбна?

```
БЕЗ CHECKPOINTER:
═══════════════════════════════════════════════════════════════

    Запуск 1:   START → researcher → writer → ... → END

    Запуск 2:   START → researcher → ...  (усё з пачатку!)

    Немагчыма працягнуць з месца спынення
    Немагчыма праглядзець гісторыю


З CHECKPOINTER:
═══════════════════════════════════════════════════════════════

    Запуск 1:   START → researcher → [ЗАХАВАНА]
                                          │
                                   thread_id: "chat-123"

    Запуск 2:   [АДНАЎЛЕННЕ] → writer → reviewer → ...
                       │
                thread_id: "chat-123"

    Можна працягнуць з месца спынення
    Можна праглядзець гісторыю
    Можна мець некалькі незалежных "размоў"
```

#### Thread ID — ідэнтыфікатар "трэда"

### Запуск графа

Нарэшце! Давайце запусцім наш граф. Функцыя `invoke()` прымае пачатковыя значэнні стану і канфігурацыю, а затым выконвае ўвесь граф ад пачатку да канца.

#### Функцыя invoke()

const result = await app.invoke(

## ЧАСТКА 6: FAQ — Частыя пытанні

### Чаму reducer для messages дадае, а для topic замяняе?

**Паведамленні** — гэта гісторыя. Мы хочам захаваць усе паведамленні за ўвесь працэс.

**Topic** — гэта бягучая тэма. Калі тэма змянілася — старая не патрэбна.

### Што будзе, калі я не ўкажу reducer?

LangGraph выкарыстае паводзіны па змаўчанні — **замена** (як для topic).

### Нашто патрэбен iterationCount?

Каб **абараніцца ад бясконцага цыкла**. Калі рэцэнзент ніколі не скажа "зацверджана", праграма будзе бясконца круціцца паміж writer і reviewer.

### Ці можа адзін вузел выклікаць іншы напрамую?

**Не.** Вузлы не ведаюць адзін пра аднаго. Яны толькі чытаюць/пішуць стан. LangGraph сам вырашае, хто выконваецца наступным, на аснове пераходаў.

### Што такое **start** і **end**?

Гэта **спецыяльныя віртуальныя вузлы**:

- `__start__` — адкуль пачынаецца граф
- `__end__` — дзе граф завяршаецца

Яны не выконваюць код — толькі пазначаюць межы.

### Ці можна мець некалькі канчатковых вузлоў?

Так! Напрыклад:

```typescript
.addEdge('success', '__end__')
.addEdge('error', '__end__')
```

| **Reducer**            | Вызначае, як аб'ядноўваць новыя даныя з існуючымі        |
| **Nodes (Вузлы)**      | Функцыі, якія апрацоўваюць стан                          |
| **Edges (Пераходы)**   | Правілы, якія вызначаюць парадак выканання               |
| **Conditional Edges**  | Дынамічны выбар наступнага вузла                         |
| **Checkpointer**       | Захаванне стану для працягу пазней                       |

### Што далей?

Цяпер, калі вы разумееце асновы, вы можаце:

1. **Пабудаваць уласную агентную сістэму** — Пачніце з простага графа з двух вузлоў і паступова дадавайце складанасць
2. **Эксперыментаваць з рознымі патокамі** — Паспрабуйце ствараць графы з некалькімі ўмоўнымі галінамі
3. **Дадаць персістэнтнасць** — Выкарыстоўвайце `MemorySaver` або checkpointer-ы на базе дадзеных для прадакшна
4. **Даследаваць прасунутыя магчымасці** — Вывучыце падграфы, паралельнае выкананне і патэрны з удзелам чалавека

### Ключавыя высновы

- **Думайце графамі**: Разбівайце ваш AI-працоўны працэс на дыскрэтныя крокі (вузлы), злучаныя правіламі (пераходамі)
- **Стан — гэта ўсё**: Уся камунікацыя паміж вузламі адбываецца праз агульны стан
- **Reducer-ы важныя**: Выбірайце правільны reducer для кожнага поля — дадаванне для гісторыі, замена для бягучых значэнняў
- **Цыклы дазваляюць ітэрацыі**: У адрозненне ад простых ланцужкоў, графы могуць вяртацца назад для дапрацоўкі

Прыклад з напісаннем артыкула, які мы пабудавалі, дэманструе рэальны патэрн: **даследаванне → напісанне → рэцэнзаванне → (паўтарыць пры неабходнасці) → фіналізацыя**. Гэты ж патэрн прымяняецца да многіх AI-прыкладанняў: рэцэнзаванне кода, мадэрацыя кантэнту, шматкрокавае разважанне і многае іншае.
